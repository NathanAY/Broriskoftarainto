# Taste
- Designer/UI-facing distance parameters (attack range, knockback, explosion/bounce/homing/orbit radii, weapon range) must be authored in **meters**, following the existing `movement_speed` stat which is already in meters/sec. Pixels are an internal boundary detail only (physics, `Vector2`, target selectors). Confidence: 0.8
- Pixel-unit values must be converted to/from meters through shared helper functions (e.g. `Stats.meters_to_px()` / `px_to_meters()`) rather than inline magic numbers scattered across call sites. Confidence: 0.75
- Tooltips that surface physical values should show explicit unit labels (e.g. `range: 1.33 m`, `knockback: 0.4 m/s`), not bare numbers. Confidence: 0.7
- UI must not use notation that implies the wrong semantics: a weapon's base stats belong to the weapon, not the holder, so they are rendered unsigned with no `+` prefix — the `+` is reserved for stat rows that actually represent a gain to the player's stats. Confidence: 0.65
- Stat lines whose bare number could be mistaken for a multiplier should be spelled as an explicit rate (e.g. `Attack Speed: 0.8 attack/sec` rather than a bare `0.8`). Confidence: 0.6
- Expects every conversion/refactor to ship with: a new test suite pinning the values, updates to existing tests that hardcoded the old units, and updates to the affected docs. Confidence: 0.7
- Runs the full gdunit suite after changes and compares `.gdunit.log` against a known baseline (warnings/errors/failures) rather than requiring a fully clean log. Confidence: 0.6
- Rejects central scripts that branch on concrete type with hardcoded `if <x> is <Type>` checks to special-case each variant; prefers an extensible design where each subtype exposes its own behaviour through overridable virtual hooks, so adding a new type is a change in that type's own file and never a new branch in the shared dispatcher. Confidence: 0.75
- Prefers deleting unnecessary indirection / derived-value code ("looks weird, not needed — just delete it") in favour of a direct model where the authored value is used as-is (one source of truth), rather than a hidden derived value that can disagree with what is displayed. Confidence: 0.65
- Wants assumptions verified empirically before designing/implementing around them (e.g. "check if Thorns works with Range: 0m first"); when a hypothesis is questionable, probe it with a real run rather than reasoning about it only. Confidence: 0.6
- UI should be complete and informative: each entity should surface its own distinguishing/meaningful properties rather than only a generic shared subset (e.g. a shotgun must show its pellet count). Confidence: 0.6
