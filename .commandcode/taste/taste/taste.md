# Taste
- Designer/UI-facing distance parameters (attack range, knockback, explosion/bounce/homing/orbit radii, weapon range) must be authored in **meters**, following the existing `movement_speed` stat which is already in meters/sec. Pixels are an internal boundary detail only (physics, `Vector2`, target selectors). Confidence: 0.8
- Pixel-unit values must be converted to/from meters through shared helper functions (e.g. `Stats.meters_to_px()` / `px_to_meters()`) rather than inline magic numbers scattered across call sites. Confidence: 0.75
- Tooltips that surface physical values should show explicit unit labels (e.g. `range: 1.33 m`, `knockback: 0.4 m/s`), not bare numbers. Confidence: 0.7
- UI must not use notation that implies the wrong semantics: a weapon's base stats belong to the weapon, not the holder, so they are rendered unsigned with no `+` prefix — the `+` is reserved for stat rows that actually represent a gain to the player's stats. Confidence: 0.65
- Stat lines whose bare number could be mistaken for a multiplier should be spelled as an explicit rate (e.g. `Attack Speed: 0.8 attack/sec` rather than a bare `0.8`). Confidence: 0.6
- Expects every conversion/refactor to ship with: a new test suite pinning the values, updates to existing tests that hardcoded the old units, and updates to the affected docs. Confidence: 0.7
- Runs the full gdunit suite after changes and compares `.gdunit.log` against a known baseline (warnings/errors/failures) rather than requiring a fully clean log. Confidence: 0.6
- Rejects central scripts that branch on concrete type with hardcoded `if <x> is <Type>` checks to special-case each variant; prefers an extensible design where each subtype exposes its own behaviour through overridable virtual hooks, so adding a new type is a change in that type's own file and never a new branch in the shared dispatcher. Confidence: 0.75
- Prefers deleting unnecessary indirection / derived-value code ("looks weird, not needed — just delete it") in favour of a direct model where the authored value is used as-is (one source of truth), rather than a hidden derived value that can disagree with what is displayed. Confidence: 0.65
- Wants assumptions verified empirically before designing/implementing around them (e.g. "check if Thorns works with Range: 0m first"); when a hypothesis is questionable, probe it with a real run rather than reasoning about it only. Confidence: 0.6
- UI should be complete and informative: each entity should surface its own distinguishing/meaningful properties rather than only a generic shared subset (e.g. a shotgun must show its pellet count). Confidence: 0.6
- Designates one entity (the default character, Multitasker) as the immutable reference/baseline that is used for tests; it must stay byte-identical across rebalances because every other value is measured against it. Confidence: 0.75
- Wants playable entities to be unique and interesting — distinct attack archetypes and identities — rather than near-identical stat clones that differ only by a couple of numbers. Confidence: 0.7
- Content that plays a role (e.g. a new archetype) is added by redesigning an existing entity rather than growing the roster with a new one, avoiding new art/registration work. Confidence: 0.55
- Source art assets must stay untouched: keep the high-resolution original and shrink it in-engine via the node's scale (`Sprite2D.scale = drawn_size / source_size`) instead of pre-downscaling or otherwise baking a resized copy. This is the default for every new generated asset — world sprites *and* UI/modifier icons alike — so nothing in the project encodes its on-screen size in the file. Discounts the quality loss of offline resampling and treats asset detail as worth preserving. Confidence: 0.9
- Per-class drawn sizes belong in one shared constant (e.g. an `AssetSizes` class holding the enemy, boss and modifier-icon widths, with a `scale_for(texture, drawn_size)` helper) that every draw site derives its scale from — not the same number repeated as a literal in each scene or script. Confidence: 0.7
- A large source texture drawn minified must import with mipmaps enabled and have its sprite filter set to `Linear with Mipmaps` — a plain linear filter does not sample mipmaps even when they exist, so both halves are required to stop aliasing/shimmer. Confidence: 0.75
- Style/art documentation must state numeric, measurable targets (thickness in px and/or as a proportion of the object's size, per asset class) rather than qualitative requirements like "needs a black border" — vague specs are what let assets drift apart, so the measured spec should be written into the doc. Confidence: 0.65
- The ink/outline band spec is **~10% of the object's bounding-box width** (8-12% acceptable), not a thin 3-5% line; the thicker, bolder outline is the intended look, and a spec that measures existing assets at 3-5% and adopts that as the rule is a misread of the intent. Confidence: 0.8
- Image-generation prompts are capped at **2000 characters**; the cap must be measured against the drafted prompt rather than estimated, and when a prompt runs long the subject adjectives get trimmed while the trailing constraint block and the orientation/border-width clauses stay intact. Confidence: 0.7
- Once an image-generation prompt has produced a usable asset, the doc should carry that prompt **verbatim** as the canonical example (a full, copy-pasteable block) rather than an abstract `{creature}` placeholder template; only the subject/creature description is meant to be swapped between generations, the rest is copied as-is. Confidence: 0.6
- Enemy sprites must be drawn **side-on, facing right** — the `Enemy` node only mirrors sprites (`sprite.flip_h`), so the unflipped texture has to already face right. A creature drawn looking forward at the camera (or at a 45°/three-quarter angle) is unusable in game and reads as permanently strafing; reference assets like `spitter.png` / `diplocaulus.png` look to the side, not at the viewer. Confidence: 0.7
- Enemy sprites must have **no legs, feet, arms, hands or separate limbs** — a single solid "blob" body with the face/ears on the front side. The `Enemy` node only scales and mirrors the sprite, so drawn legs can never animate and read as broken; a legless design is the project's visual rule (see the visual-design doc) and every enemy prompt must say so explicitly in both the subject and the negative-clause block. Confidence: 0.7
- Wants strictly scoped changes: when the request is to revise a single artifact (e.g. an image-generation prompt), nothing else in the repo may be added or modified — helper/debug scripts and similar unrequested churn get called out and reverted. Confidence: 0.75
- Prefers character visuals assembled from composable, separately authored parts (body + eyes + mouth overlays on a shared canvas) over pre-baked combined images like `<id>_icon.png`; the flexibility to mix and reuse parts across characters is the point, so anything that hardcodes a single combined sprite is a legacy artifact to remove rather than keep alongside the new system. Confidence: 0.7
- Prefers balance bands that leave room for archetype identity (roughly ±30% offense / ±60% survivability around the reference) over tight or exact parity, tolerating deliberate, explicitly-documented exceptions (e.g. a glass-cannon character kept above the band on clear power). Confidence: 0.6
