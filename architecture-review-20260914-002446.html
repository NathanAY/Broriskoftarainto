1. Collapse the damage pipeline into one deep module

Strong in-process
src/Systems/weapon/projectile.gd:85-101 · melee_weapon_node.gd:255-271 · contact_weapon.gd:57-76 · area_weapon.gd:13-29 · src/Scripts/explosion.gd:42-59 · src/Systems/damage/health.gd · damage_context.gd

before · five copies, two event managers, no owner

flowchart LR P[projectile.gd] --> H1[attacker EventManager] M[melee_weapon_node] --> H1 C[contact_weapon] --> H1 A[area_weapon] --> H1 E[explosion.gd] --> H1 H1 --> D[DamageContext.final_amount mutated] D --> H2[defender EventManager] H2 --> H[health.take_damage] H --> H1 H1 -.-> X[(after_deal_damage)] style X fill:#fee2e2,stroke:#dc2626

The same 9-hop sequence written in 5 places. Event payload shapes disagree per emitter at src/Systems/weapon/projectile.gd:101, contact_weapon.gd:76, area_weapon.gd:29, explosion.gd:59 — and on_health_changed fires before target_take_persent_damage is written (health.gd:18-19).

after · one interface, ordering owned once

deal_damage(source, target, amount, tags)
implementation (internal)
build DamageContext
before_deal_damage · before_take_damage
take_damage · after_take_damage
after_deal_damage · on_hit
ordering stated once, here
projectile.hit → deal_damage
melee swing → deal_damage
contact / area / explosion → deal_damage

Problem

The hit sequence has no owner: do_damage is re-implemented across 5 damage sources, each with its own source semantics and payload shape, while ordering between two event managers is an accident of listener order.

Solution

Move the whole hop sequence behind one module the damage sources call. Its interface stays the same shape across all five callers; final_amount mutation and event ordering become its implementation.

Wins

  • locality: ordering bugs fixed once
  • tests hit one interface, whole pipe
  • delete 4 shallow pass-throughs
  • leverage: one pipe, 5 callers

2. Turn the event contract into a checked seam

Strong in-process
src/Scripts/LocalEventManager.gd · emitters: stats.gd, health.gd, weapon_holder.gd, item_holder.gd, projectile.gd, melee_weapon_node.gd, contact_weapon.gd, area_weapon.gd, explosion.gd · subscribers: ~40 modifier/UI call sites

before · interface as wide as the implementation

40-line implementation

implied interface:
~14 event names + payload shapes
kept only in a comment

subscribe/unsubscribe/emit are tiny — but the load-bearing facts every caller must know (event names, payload keys, listener arity) live in a stale comment at LocalEventManager.gd:23-40. Mismatches verified across the codebase: on_condition_change emits condition_name, item_holder.gd:48 reads ev["name"] · two on_stat_changes subscribers expect two args, the emitter sends one dict · on_weapon_changes has two shapes.

after · contract absorbed into the implementation

event-name + payload registry,
arity + key checks, one place

thinner interface

The seam grows depth: payload schema becomes part of the module's implementation, surfaced as a violation at subscribe/emit time instead of silent no-ops three calls deep.

Problem

The bus is deep on routing but shallow on contract — every event name, payload key, and listener arity is a fact leaked to callers, validated nowhere.

Solution

Register declared event schemas behind the bus seam; emit/subscribe check payloads and arities when they cross it, so shape drift becomes immediate, local, catch-it-in-a-test errors.

Wins

  • locality: one schema, N callers
  • tests name payload shape, not silence
  • two arity bugs surface as errors
  • the comment becomes a runtime check

At least three different back-channels for "who is my holder": get_node on children, event_manager.get_parent(), get_parent().hold_owner. character.gd:21-23 attaches modifiers to every child, item_holder.gd:37-38 attaches them again.

after · parts cross one seam, injected at construction

flowchart LR E[Character / Enemy] --> CTX["entity context (attribute access)"] CTX --> S[Stats] CTX --> EM[EventManager] CTX --> H[Health] MW["Weapons / Modifiers / Buffs / items"] --> CTX PJ["projectile.gd"] --> CTX style CTX fill:#1e293b,color:#e2e8f0

Tree-shape knowledge concentrates in one module each entity provides; every subsystem takes that context rather than walking nodes or reaching through parents.

Problem

The "entity" concept is a wide, implicit node-name contract (Stats, EventManager, Health) rediscovered by ~30 call sites through different back-channels, plus a duplicated combatant body between character.gd and Enemy.gd.

Solution

Entities expose their parts once, at a single seam; subsystems receive them as parameters. Character and Enemy keep one shared implementation of that seam (shared death/flash/collision wiring).

Wins

  • locality: tree shape known in one place
  • tests build entities without scenes
  • identical Entity/Character bodies collapse
  • the "holder" back-channel dies

Strong local-substitutable

before · six entry points, four near-copy pairs

flowchart TD G[get_item_by_type] --> S1[_generate_stat_item] G --> S2[_generate_stat_item_insexed] G --> E1[_generate_effect_item] G --> E2[_generate_effect_item_insexed] G --> B1[_generate_buff_item] G --> B2[_generate_buff_item_insexed] G --> D1[_generate_debuff_item] G --> D2[_generate_debuff_item_insexed] R[generate_random_item] --> G P[get_item_from_pool_or_generate] --> R S1 -.duplicate.-> S2 E1 -.duplicate.-> E2 B1 -.duplicate.-> B2 D1 -.duplicate.-> D2 classDef dup fill:#fee2e2,stroke:#dc2626; class S1,S2,E1,E2,B1,B2,D1,D2 dup

The negative-stat + description block is copy-pasted ~8 times (040-108 typo "Decreasese" among them); _stat/_effect thresholds computed but never used; an unreachable branch at :95; _generate_stat_modifiers' elif is byte-identical to its else.

after · one generate, table-driven inside

generate(kind, index?)
implementation (internal)
kind table → stat / effect / buff / debuff
one "negative stat" helper, used 4x
name + description built in one place
indexes and randomness are one parameter

Problem

The generator is shallow: six public entry points and near-copy ×2 variants for each item kind, so the interface takes as long to learn as the implementation takes to read. Every new item kind means the whole pattern repeats twice.

Solution

One generate entry with a kind selector; index-or-random is a parameter, and stat/name/description/negative-stat work are shared helpers inside the module.

Wins

  • interface shrinks 6 entry points → 1
  • locality: negative-stat logic in one helper
  • tests assert one coherent generation
  • dead thresholds + branch removed
ItemFactory depends on a live $Stats child to enumerate stat keys — the factory's test seam is currently a whole scene. A data-driven source of stat names would make the single generate interface substitutable with an in-memory adapter.

5. Own item application — dedup, stacking, and cleanup in one policy

Worth exploring in-process
src/Systems/Items/item_holder.gd (add_item: 47 lines, 12 behaviors) · src/Systems/Items/Item.gd · src/Systems/Items/Buffs/ · test/Systems/Items/

before · one procedure carrying 3 bugs

add_item(item)
└ dedup by scene path ✗ empty for factory items
└ apply_to(holder) ✗ skipped on stacked effects
└ condition-gate stack ✗ reads wrong key
└ add_stack / attachEventManager
└ emit on_item_added
remove_item(item)
└ stat modifiers removed
└ effect node, subscriptions, timers ✗ left alive

after · stack policy is a deepened module

ItemHolder.add_item / remove_item
implementation (internal)
stable dedup key for .tres and packed scenes
apply-on-stack always runs
condition-gate reads the emitted key
removal frees effect + subscriptions + timers

Problem

add_item is a 12-behavior procedure covering dedup, effect instantiation, duck-typed attachment, stacking, condition gates and events — and three of its decisions are currently wrong (see red ✗ above). Its interface hides nothing from the reader.

Solution

Extract the stacking policy — dedup key, apply-on-stack, condition gate, removal cleanup — as a module behind the holder. The holder keeps the add/remove interface; the policy owns how stacks are decided and undone.

Wins

  • locality: three bugs in one module
  • the missing remove_item test finds a home
  • stacking rules stated once

6. A shared base for 22 modifier adapters

Worth exploring local-substitutable
src/Systems/Items/Modifiers/ (22 scripts, ~1310 lines) · attached by item_holder.gd:37-38 and character.gd:21-23

before · scaffolding copied 22 times, drifting

each modifier carries the same header + stack triad, written slightly differently each time:
attachEventManager(em) · holder = em.get_parent() · stats = holder.get_node("Stats") · subscribe("on_hit", ...) · add_stack · remove_stack · set_stack_active
14× stacks: Array[bool]
regen: int
8× no triad
handler names jumbled: _on_triger · _on_trigger · _on_event · _on_on_hit

after · shared base, thin adapters

StackableModifier (base)
implementation (internal)
attachEventManager + holder/stats discovery
stacks + add/remove/set_stack_active (one type)
on_stat_changes re-cache helper
the event→response delta is the only thing an adapter keeps

Problem

Twenty-two adapters sit at the same seam and re-write ~300 lines of identical attach/stack/cache scaffolding — with real drift (two stack types, four handler-name spellings, a debug prints that appears in some and not others). None extend a shared base.

Solution

One base that owns attachment, stacking and stat-cache refresh — the parts that genuinely don't vary. Each modifier keeps only its event→response body, the two things that actually differ (as recommended in docs/ai_overview.md: "small, self-contained modules").

Wins

  • locality: attach/stack fixed in one base
  • ~300 lines of drift absorbed
  • one stack type, no spelling lottery
  • leverage: new modifiers become thin
One adapter would be a hypothetical seam — here there are 22, so the seam is real. The risk is a base that over-abstracts: the grilling loop should decide what stays behind it by deletion-testing each copied idiom against the one modifier that genuinely varies.

Top recommendation

Start with candidate 1 — the damage pipeline. It is where the codebase is deepest and owning exactly nothing: five identical copies of the same 9-hop sequence, each with its own payload shape and source semantics, and the ordering bug in health.gd:18-19 that a single module would fix once. It is also the only candidate with a clean deletion test — every damage source (projectile, melee, contact, area, explosion) calls the same module, so complexity concentrates instead of moving. And it pays for itself immediately with a test that exercises the entire pipe through one interface, which is exactly what candidates 2 and 6 (the event contract and the modifier base) then build on.

Working on items recently? Then candidate 4 — ItemFactory is the best second pick; it is self-contained, its interface change is backward-compatible with the shop, and it makes the generator testable without a full scene.
